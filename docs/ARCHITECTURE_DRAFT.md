# Architecture

## Confirmed deployment topology

```text
Browser
  → Vercel / Next.js
      → public API Gateway (Docker, one worker and one replica)
          → in-memory sessions + rate/concurrency state
          → private Document Parser Service (Docker)
          → private Agent Service (Docker)
              → optional Gemini API
```

Only the Gateway is public. Parser and Agent containers share a private backend network and expose health/service ports only inside that network. All three backend services must be long-running; serverless functions are not compatible with the current background task and in-memory session model.

## Request lifecycle

1. Frontend uploads a CV PDF and supplies exactly one JD source: pasted text or a JD PDF.
2. Gateway validates input, applies per-client rate and global concurrency limits, and creates a temporary session.
3. Gateway returns `202` and a session ID for internal polling, without displaying that ID to the user.
4. The background task parses the CV and optional JD PDF, then Agent parses the resulting CV/JD text, matches evidence, calculates `phase6-v2`, and chooses a generation branch.
5. Gateway stores the completed result or sanitized error in memory. The terminal update starts a new 30-minute TTL.
6. Frontend polls the no-store session endpoint. Restart or expiry intentionally removes the result.

`X-Request-ID` is accepted/generated by the Gateway, returned to the caller, and propagated to both internal services. Logs contain IDs, paths, status, downstream name, and timing—not raw CV/JD content.

## State and scaling

Sessions, request windows, and active-analysis counters are protected by in-process locks but are not shared. `MAX_SESSIONS=500`, `SESSION_TTL_MINUTES=30`, and `MAX_CONCURRENT_ANALYSES=3` are configurable. This avoids database/account complexity but explicitly requires one Gateway process. A shared store/queue is a future scaling change, not part of this MVP.
